# ADR-001: граница Vanilla JS vs Rust/WASM в PUMP

Дата: 26.11.2026. Статус: принято. Основание: измерение, а не предположение
(`web/bench/*`, `tests/bench_dsp.py`, `web/bench/baseline.json`).

## Контекст

Одинаковый тракт (10 RBJ-биквадов transposed-DF2 + preamp, `crates/audio-dsp-engine/src/eq.rs`
vs `web/bench/js-dsp.js`) прогнан в HeadlessChrome 153 бок о бок: 3 прогона +
1 прогон с 4x CPU-throttle, 15 пачек x 256 блоков x 128 фреймов, warmup 3 пачки,
детерминированный вход (xorshift). WASM: `web/pkg/pump_dsp.wasm`, ABI v1
(`config_len=57`, `capacity=2048`).

## Факты (после симметризации копирования входа, 26.11.2026)

- Холодный старт (типично): compile 0.4–2.6 мс + instantiate 0.2–1.2 мс
  (зависит от загрузки машины; прогон 1: 2.6 + 1.2).
- Размер WASM: 61951 байт raw, 25154 байт gzip -9 (40.6%; измерено скриптом,
  пишется в `baseline.json:wasm_bytes`).
- Core (ядро, нс/фрейм, p50 / p95 / p99; прогон 1):
  JS 106.81 / 393.68 / 393.68; WASM 54.93 / 177.00 / 177.00.
  Отношение 0.514 — WASM быстрее в ~1.8–1.9 раза (диапазон по прогонам
  0.514–0.545). xRT медианный: JS ~195, WASM ~379.
- Full (с границей JS/WASM): JS p50 103.76, WASM p50 57.98.
  Накладные расходы ABI: full−core = 1 квант таймера (см. честность ниже).
- Память EQ-ядра: Linear Memory 1638400 байт до и после, `mem_grew=false`
  во всех прогонах. Факт относится ТОЛЬКО к EQ-ядру; анализ (`music_analysis`)
  держит ~13 f32/STFT-кадр + моно-микс и лимитирован 300 с / 28.8M кадров
  (см. ADR-002), его память — отдельным измерением.
- CPU-throttle 4x (прогон 1): JS p50 442.50 нс, WASM p50 238.04 нс
  (отношение 0.538); xRT 47.1 vs 87.5 — соотношение то же,
  вывод не артефакт быстрой машины.
- Идентичность: `checksum_rel_diff = 0` во всех 4 прогонах (3 + throttled).
- Квант 128 фреймов = 2.67 мс: блок WASM ~7 мкс, JS ~13 мкс — оба < 0.5% ядра.

## Честность чисел (поправка ревью)

- `performance.now()` без изоляции клампится 100 мкс; пачка 32768 фреймов →
  шаг квантования 100 мкс/32768 = 3.05 нс/фрейм. Все p50 кратны 3.05
  (34 и 18 квантов). Разница full−core у WASM = ровно 1 квант → истинная
  накладная стоимость ABI лежит в [0, ~6] нс/фрейм, «+5.6%» — артефакт
  округления. Аналогично «1.89x»: по трём прогонам диапазон ~1.8–1.9x, ±1 квант.
- В обоих full-циклах harness есть `% input.length` на каждый сэмпл, которого
  нет в реальном `dsp-worklet.js`: full включает искусственный modulo
  одинаково для JS и WASM; граница JS (full≈core) этим harness не измерена.
- SIMD не измерялся: бенч шёл без `+simd128`, rustfft на wasm32 без
  target-feature берёт скалярный путь. «SIMD-дружелюбный» в решении —
  про структуру алгоритмов, а не замеренный факт.

## Решение

1. EQ-ядро остаётся в Rust/WASM (уже там, корректно, быстрее в ~1.8–1.9 раза).
   Мелкие задачи (UI-состояние, очередь, подсветка слов, комнаты) остаются в JS:
   при бюджетах < 0.5% кадра перенос в WASM не окупает ABI и сложность.
2. Новый compute-heavy анализ (STFT/chroma/onset/BPM/key/LUFS — алгоритмы,
   дружелюбные к векторизации; замеров SIMD нет, см. честность выше)
   — Rust + realfft в независимом ядре без Tokio/Axum/DOM (`audio-dsp-engine`,
   feature `analysis`). WASM-интеграция анализа — только после цифр native/WASM
   паритета на том же ядре.
3. Пороги: `checksum_ok` обязателен; perf-медианы из `baseline.json` —
   ориентиры, тревога при регрессе > 2x к медиане (предупреждение, не gate).

## Что не делаем

- Не тащим DOM/Tokio/Axum/Telegram в вычислительное ядро.
- Не выдаём синтетические фикстуры за доказательство качества на реальной музыке
  (для реальной музыки — отдельный размеченный набор и отдельное измерение).
